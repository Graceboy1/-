# 开发过程与 Git 提交说明

## 当前缺口

当前交付是本地工作目录的源码快照，没有随附可核验的完整历史 Git 仓库。ZIP、文件修改时间、聊天记录和本说明不能代替比赛要求的真实完整 Git 提交历史。此项须由参赛者在提交前解决或如实咨询组委会，不能因代码可运行就自动视为满足。

应先检查本人原始 GitHub/Gitee 仓库、其他开发目录、备份或远程分支是否保留真实历史。若存在，保留原提交身份与时间并提供评审权限；不得依据聊天描述补造旧提交、回填日期、改写作者或批量生成假模块记录。

若确无旧历史，应如实说明目前只有快照，询问组委会是否接受现状或需要其他真实过程证据。聊天及操作记录只能作额外佐证，不是 Git 历史。能否认可由组委会判断，本项目不能保证不影响资格或评分。

## 从现在开始真实记录

### GitHub创建页的两个选项

“添加.gitignore”先选“没有.gitignore”：本项目源码快照已经包含针对Python、Next.js、密钥和数据目录的.gitignore，解压后应把该文件连同源码提交，避免网站生成模板覆盖已有规则。忽略规则用于排除文件，不会清除已经进入Git历史的秘密。官方说明：https://docs.github.com/zh/get-started/git-basics/ignoring-files 。

“添加许可证”暂选“无”：用户提供的比赛要求没有指定开源许可，本次没有代替团队授予整体开源权利；待团队确认原创代码与第三方素材的权利后再决定。公开可见不等于采用开源许可证，原有第三方库的许可证仍须保留。官方说明：https://docs.github.com/zh/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/licensing-a-repository 。

源码在材料包中的01号ZIP，解压后进入contest-edition目录，仓库根目录应直接看见README.md、server、web、requirements.txt、.gitignore和.env.example。不要把整个材料包ZIP、供应商数据、账号数据库或原开发目录拖入仓库。若GitHub创建页已自动建立README提交，可先克隆该真实仓库，再把经过核对的源码文件放入克隆目录，保留已有历史；不要强制推送覆盖远程。

### 实际提交原则

以下仅为操作指南，本次准备未代为初始化、提交、推送或公开仓库。

1. 选用干净源码目录，核对 .gitignore、空值 .env.example 与待提交文件，不纳入真实 .env、数据库、日志、行情库或五席位原包。
2. 参赛者自行创建 GitHub/Gitee 仓库，公开或授权前确认代码素材权利、团队信息范围和评审可访问性。
3. 新建仓库的首笔只能诚实标为“当前源码初始快照”，使用实际当前日期，不声称包含早期开发过程。它不能恢复缺失历史。
4. 后续每次真实功能、测试或文档改动正常提交，说明动机、改动和验证结果。不能把已存在文件拆成多笔假装逐步开发。
5. 提供实际发布版本或标签，检查权限并保留官方提交回执。按要求提交后不擅自改动。

## 已有仓库核查命令

```powershell
git status --short
git log --date=iso --format="%h %ad %an %s" --all
git remote -v
git ls-files
git check-ignore .env .workspace-account.sqlite3 .research-records.sqlite3
```

remote 输出可能含私有地址或嵌入式凭据，不原样录屏或公开。check-ignore 只证明忽略规则匹配，不能证明密钥未曾进入历史，仍需检查已跟踪内容和历史。如果凭据曾公开，应由本人立即在服务商处撤销或轮换，并处理泄露，不能只删当前文件。

可保留真实需求、设计、AI 辅助、人工复核和失败修复记录，但不要把后来补写的总结说成当时原始记录。代码和当次实测可验证当前工具调用、预案和存储行为，不能倒推开发日期或作者贡献。
